## 1. Цели и предпосылки

### 1.1. Зачем идем в разработку продукта?
- **Бизнес-цель:** Автоматизировать мониторинг реакций для оперативного выявления негатива, улучшения модерации и повышения вовлеченности.
- **Почему станет лучше:** Текущий ручной анализ 500k комментариев/день медленный и субъективный. ML позволит проверять 100% контента в реальном времени, снижая риски штрафов РКН.
- **Успех итерации:** Внедрение базовой модели классификации, покрывающей >90% потока комментариев с точностью (F1) > 0.8.

### 1.2. Бизнес-требования и ограничения
- **Бизнес-требования:** Автоматическое скрытие токсичного контента, приоритизация очереди для модераторов, аналитические отчеты по настроениям.
- **Бизнес-ограничения:** Соответствие требованиям РКН (удаление в течение 24ч, для некоторых категорий — быстрее), бюджет на GPU-инференс.
- **Успешный пилот:** Снижение времени реакции на негатив до < 5 минут, уменьшение нагрузки на модераторов на 50%.

### 1.3. Что входит в скоуп проекта/итерации
- **Входит:** Разработка классификатора тональности (3 класса) и детектора токсичности, интеграция с Kafka, базовый API.
- **Не входит:** Анализ видео/изображений, сложная система рекомендаций на основе настроений.
- **Техдолг:** Оптимизация модели под ONNX/TensorRT, расширенная система Active Learning.

### 1.4. Предпосылки решения
- Используем текстовые данные комментариев.
- Гранулярность: каждый отдельный комментарий.
- Горизонт: реальное время (streaming).

## 3. Подготовка пилота

### 3.1. Способ оценки пилота
- A/B тестирование: Группа А — ручная модерация, Группа Б — ML-фильтрация + ручная проверка спорных случаев.

### 3.2. Что считаем успешным пилотом
- Сокращение False Negative (пропущенный негатив) на 30%.
- Ускорение модерации критических нарушений в 10 раз.

## 4. Внедрение

### 4.1. Архитектура решения
Подробное описание архитектуры, диаграммы компонентов и последовательности доступны в [docs/architecture/README.md](docs/architecture/README.md).

### 4.2. Описание инфраструктуры и масштабируемости
- **Стек:** Kafka, Kubernetes (K8s), Triton Inference Server, ClickHouse.
- **Масштабируемость:** Горизонтальное масштабирование воркеров инференса в зависимости от длины очереди в Kafka.

### 4.3. Требования к работе системы
- **SLA:** 99.9% доступность.
- **Latency:** < 200ms на инференс одного сообщения.
- **Throughput:** до 1000 сообщений в секунду.

### 4.4. Безопасность системы
- Изоляция ML-воркеров в закрытом контуре.
- Аудит всех действий автоматики и модераторов.

### 4.5. Безопасность данных
- Хранение персональных данных согласно ФЗ-152.
- Обезличивание данных перед использованием в обучении (удаление ФИО, телефонов).

### 4.6. Издержки
- Основные затраты: аренда GPU-инстансов, хранилище ClickHouse для логов.

### 4.7. Integration points
- Вход: Kafka topic `raw_comments`.
- Выход: Kafka topic `moderated_actions`, API для фронтенда модераторов.

### 4.8. Риски
- "Отравление" обучающей выборки (Data Poisoning).
- Резкое изменение сленга или появление новых тем (Concept Drift).
