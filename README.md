## 1. Описание кейса

### Бизнес-цель

Автоматизировать мониторинг пользовательских реакций на контент (посты, рекламу, новости) в социальной сети, чтобы оперативно выявлять негатив, улучшать модерацию и повышать вовлечённость аудитории.

### Текущая ситуация (проблематика)

- Анализ тональности проводится **вручную** (модераторы читают выборочные комментарии) или **не проводится вообще** — процесс медленный, дорогой, субъективный.
- Ежедневный поток комментариев — **до 500 000**.
- Со стороны РКН ведётся мониторинг качества модерации: потенциально неприемлемые комментарии могут повлечь **серьёзные штрафы и санкции**.

### Целевое состояние

ИИ-система **Sentinel AI**, которая в реальном времени:
1. Классифицирует тональность и токсичность каждого комментария
2. Автоматически принимает решения по очевидным случаям (≥ 85% трафика)
3. Эскалирует пограничные случаи модераторам с подсказками ИИ
4. Обеспечивает аналитику трендов тональности для контент-менеджеров
5. Непрерывно дообучается на основе фидбека модераторов

## 2. Модели бизнес-процессов

### 2.1. Процесс «КАК ЕСТЬ» (As-Is)

Ручная модерация с выборочным покрытием. Подробная модель:

→ [BPMN-диаграмма As-Is](diagrams/bpmn/as-is.md)

**Ключевые проблемы:**
- Охват: < 5% комментариев проверяется
- Время реакции: 4–24 часа
- Субъективность: зависит от конкретного модератора
- Риск штрафов РКН: высокий

### 2.2. Процесс «КАК ДОЛЖНО БЫТЬ» (To-Be)

ИИ-автоматизированная модерация с эскалацией сложных случаев. Подробная модель:

→ [BPMN-диаграмма To-Be](diagrams/bpmn/to-be.md)

**Что меняет ИИ-система:**

| Аспект | As-Is | To-Be |
|---|---|---|
| Охват | 3–5% | 100% |
| Скорость реакции | 4–24 часа | < 1 секунда (85%+) |
| Объективность | Субъективная | Единая модель с порогами |
| Стоимость | Линейный рост ФОТ | Фиксированные расходы |
| Риск штрафов РКН | Высокий | Минимальный |
| Аналитика | Отсутствует | Реалтайм дашборды |

## 3. Структура данных

Система использует **гибридную распределённую архитектуру данных**, где каждое хранилище подобрано под паттерн доступа.

→ [ER-диаграмма и модели данных](diagrams/data/er-diagram.md)

### 3.1. Обоснование распределённого хранения

| Хранилище | Тип | Назначение | Причина выбора |
|---|---|---|---|
| **PostgreSQL** | Реляционная | Основные сущности (пользователи, посты, решения модерации) | ACID-гарантии для юридически значимых операций |
| **MongoDB** | Документная | Сырые входящие комментарии | Высокая скорость записи, гибкая схема, горизонтальное масштабирование |
| **ClickHouse** | Колонковая | Аналитика, агрегация трендов | OLAP-запросы в 10–100x быстрее PostgreSQL |
| **Redis** | In-memory | Кэш ML-моделей, rate limiting | Суб-миллисекундный доступ для инференса |
| **S3** | Объектное | Артефакты ML-моделей, логи аудита | Долговременное хранение больших файлов |

### 3.2. Потоки данных

Данные перемещаются между хранилищами через **Apache Kafka**, обеспечивающий:
- Децентрализацию продюсеров и консьюмеров
- Гарантию доставки (at-least-once)
- Возможность реплея при обновлении модели
- Горизонтальное масштабирование обработки

## 4. Архитектура системы

Микросервисная архитектура с событийно-ориентированным взаимодействием через Apache Kafka.

→ [Диаграмма архитектуры системы](diagrams/architecture/system-architecture.md)

### 4.1. Слои архитектуры

1. **Клиентский слой** — веб-приложение, мобильное приложение, панель модератора, аналитический дашборд
2. **API Gateway** — маршрутизация, аутентификация, rate limiting
3. **Слой приёма данных** — Comment Ingestion, Post, User сервисы
4. **ИИ-ядро** — Sentiment Analysis, Toxicity Detection, Topic Classification, Decision Engine
5. **Слой модерации** — Escalation, Moderator Decision, Feedback Collector
6. **Аналитический слой** — Trend Aggregator, Alert Service, Report Generator
7. **ML-Ops** — Training Pipeline, Model Registry, Model Serving
8. **Распределённое хранилище** — PostgreSQL, MongoDB, ClickHouse, Redis, S3

### 4.2. Почему работа с данными носит распределённый характер

Разделение данных продиктовано **фундаментально разными паттернами доступа**:

- **OLTP vs OLAP**: транзакционные операции (модерация, баны) требуют ACID в PostgreSQL; аналитические запросы на миллионах строк требуют ClickHouse
- **Задержка**: Redis для <1 мс доступа к ML-моделям; S3 для долговременного хранения с задержкой 100–500 мс
- **Формат данных**: структурированные (PostgreSQL) vs полуструктурированные (MongoDB) vs временные ряды (ClickHouse) vs бинарные артефакты (S3)
- **Масштабирование**: MongoDB шардируется горизонтально для приёма 500K комментариев/день; ClickHouse масштабируется для терабайт аналитики

## 6. UML-диаграмма классов

→ [Диаграмма классов](diagrams/uml/class-diagram.md)

### 6.1. Ключевые сущности домена

- **Comment** — комментарий пользователя с привязкой к посту и автору
- **User** — пользователь с репутационным счётом и историей нарушений
- **SentimentResult** — результат ИИ-анализа тональности (оценки, метки, уверенность)
- **ModerationDecision** — решение о модерации (автоматическое или ручное)
- **DecisionReview** — верификация решения модератором (фидбек для дообучения)
- **MLModel** — ML-модель с версионированием и метриками качества

### 6.2. Доменные сервисы

- **CommentIngestionService** — приём и обогащение комментариев
- **SentimentAnalysisService** — инференс моделей тональности/токсичности
- **DecisionEngineService** — принятие решений на основе оценок ИИ и порогов
- **EscalationService** — маршрутизация пограничных случаев модераторам
- **AnalyticsService** — агрегация и выявление трендов тональности
- **ModelTrainingService** — дообучение и развёртывание моделей

## 8. Ключевые технические решения

### 8.1. Выбор ML-моделей

| Задача | Модель | Обоснование |
|---|---|---|
| Тональность (русский язык) | RuBERT / DeepPavlov | SOTA для русского NLP, поддержка тонкой настройки |
| Токсичность | Мультимодельный ансамбль | Повышенная точность через комбинирование |
| Тематика | Латентно-семантический анализ + BERT | Точность классификации по категориям контента |

### 8.2. Пороговые значения для автоматических решений

| Уверенность модели | Действие |
|---|---|
| confidence ≥ 0.92 | Автоматическое решение (85% трафика) |
| 0.7 ≤ confidence < 0.92 | Эскалация модератору с подсказками ИИ |
| confidence < 0.7 | Обязательная ручная модерация |

### 8.3. Стек технологий

| Слой | Технология |
|---|---|
| Backend | Python (FastAPI), Go (high-throughput сервисы) |
| ML | PyTorch, Transformers (Hugging Face) |
| Message Queue | Apache Kafka |
| Базы данных | PostgreSQL, MongoDB, ClickHouse, Redis |
| Object Storage | S3-совместимое (MinIO) |
| Container Orchestration | Kubernetes |
| Monitoring | Prometheus + Grafana |
| ML Serving | NVIDIA Triton / vLLM |
| CI/CD | GitHub Actions |

## 10. Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Ложные срабатывания (удаление легитимных комментариев) | Средняя | Высокое | Порог 0.92 для автоудаления, обязательная эскалация при низкой уверенности |
| Дрейф модели (изменение языка трендов) | Средняя | Среднее | Регулярное дообучение на фидбеке модераторов, canary deployment |
| Пиковые нагрузки (viral-посты) | Высокая | Среднее | Kubernetes HPA, Kafka буферизация, rate limiting |
| Штрафы РКН при сбоях ИИ | Низкая | Критическое | Fallback на ручную модерацию, мониторинг покрытия |
| Утечка персональных данных | Низкая | Критическое | Шифрование, минимизация данных, аудит доступа |
