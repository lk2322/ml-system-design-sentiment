## 1. Цели и предпосылки

### 1.1. Зачем идём в разработку продукта

Продукт решает три критические проблемы социальной платформы с ежедневным потоком до 500 000 комментариев:

**1. Неприемлемый масштаб ручной модерации.** Сегодня модераторы физически могут проверить 3–5% комментариев. В абсолютных цифрах — 15 000–25 000 из 500 000. Остальные 475 000+ остаются без какой-либо оценки тональности и токсичности. Это не «неудобство» — это системный провал: любая токсичная или нарушающая законодательство публикация с вероятностью >95% останется незамеченной на часы или дни.

**2. Регуляторный риск.** РКН активно мониторит крупные площадки. Штрафы за недостаточную модерацию составляют от 800 000 ₽ за однократное нарушение до блокировки ресурса при систематических нарушениях (ст. 15.1 ФЗ-149). При текущем охвате в 5% Platform практически гарантированно получает повторные нарушения — вопрос не «если», а «когда».

**3. Отсутствие аналитики тональности.** Нет инструментов для отслеживания трендов негатива вокруг контента. Рекламодатели не получают данных об эмоциональном фоне своих кампаний. Редакция не видит всплесков негатива вокруг новостей. При этом команде модерации недоступна даже базовая агрегация: «какая доля комментариев за последний час оценивается как негативная?».

ML-решение кардинально меняет картину потому, что **модели не устают, не субъективны и масштабируются линейно с аппаратными ресурсами**. Модель, обученная на размеченных данных с едиными критериями, применяет эти критерии одинаково к каждому из 500 000 комментариев — 24/7, с задержкой <1 секунды.

### 1.2. Почему станет лучше, чем сейчас, от использования ML

| Аспект | Без ML (сейчас) | С ML (после внедрения) | Почему ML лучше |
|---|---|---|---|
| **Охват** | 3–5% комментариев | 100% комментариев | Модель обрабатывает каждый комментарий без пропусков |
| **Скорость** | 4–24 часа (ручная очередь) | < 1 секунда (85%+ случаев) | Модель инферится за миллисекунды; модератор участвует только в 15% пограничных случаев |
| **Объективность** | Зависит от модератора, настроения, контекста | Единые пороги, формализованные критерии | Модель применяет одинаковую логику ко всем данным; пороги настраиваются и аудитируются |
| **Масштабируемость** | Линейный рост ФОТ с ростом трафика | Фиксированные затраты на инфраструктуру + горизонтальное масштабирование GPU | Добавление GPU-узлов дешевле найма модераторов; нет потолка Scaling |
| **Аналитика** | Отсутствует | Реалтайм тренды, алерты, дашборды | Модель генерирует структурированные оценки для каждого комментария — агрегация тривиальна |
| **Обучаемость** | Зависит от обучения модераторов | Непрерывное дообучение на фидбеке | Модель улучшается с каждым тысячным решением модератора; человек — нет |

**Ключевой аргумент**: ML не заменяет модераторов, а **повышает их эффективность в ~7x**. Вместо 500 000 комментариев модераторы проверяют ~75 000 пограничных — и каждый с подсказками ИИ (оценка, уверенность, аргументация). Это качественно другой уровень работы.

### 1.3. Бизнес-требования и ограничения

#### Бизнес-требования

| ID | Требование | Приоритет |
|---|---|---|
| BR-1 | Охват 100% входящих комментариев тональностным анализом | Критический |
| BR-2 | Автоматическое решение для ≥85% комментариев (без участия модератора) | Критический |
| BR-3 | Время реакции на токсичный контент: < 30 секунд от публикации до действия | Высокий |
| BR-4 | Эскалация пограничных случаев модератору с ИИ-подсказками | Высокий |
| BR-5 | Реалтайм-дашборд с трендами тональности по категориям контента | Средний |
| BR-6 | Пороговые алерты при всплесках негатива (настраиваемые пороги) | Средний |
| BR-7 | Сбор фидбека модераторов для дообучения модели | Критический |
| BR-8 | Аудит-лог всех решений (автоматических и ручных) для РКН | Критический |
| BR-9 | Интеграция с существующей платформой (API, вебхуки) | Высокий |
| BR-10 | Возможность настройки порогов модерации без переобучения модели | Средний |

#### Ограничения

| Категория | Ограничение | Обоснование |
|---|---|---|
| **Регуляторные** | Все решения об удалении контента должны быть объяснимыми (требование РКН) | Модель должна предоставлять не только оценку, но и объяснение решения |
| **Юридические** | Персональные данные пользователей обрабатываются в рамках 152-ФЗ | Минимизация данных в ML-пайплайне, шифрование, аудит доступа |
| **Финансовые** | Бюджет на инфраструктуру: GPU-серверы + хранение ≤ 2 млн ₽/мес на старте | Определяет выбор моделей (RuBERT-medium vs large) и архитектуру инференса |
| **Временные** | Пилот — 2 месяца, MVP — 4 месяца, production — 6 месяцев | Ограничивает количество итераций на обучение моделей |
| **Организационные** | Команда 2-3 человека: Product Owner + Data Architect + Data Engineer/Scientist | Ограничивает сложность архитектуры; предпочтение готовых решений (Kafka, Kubernetes) |
| **Данные** | Нет готового размеченного датасета тональности для домена соцсети | Необходимо разметить исторические данные → увеличивает время пилота |
| **Согласие пользователей** | Обработка комментариев допустима только в рамках Пользовательского соглашения | Некоторые типы данных могут потребовать отдельного согласия |

### 1.5. Процесс пилота и критерии успеха

#### Фаза 1: Подготовка данных (недели 1–2)

1. Выбор исторических данных: не менее 200 000 комментариев за последние 6 месяцев, сбалансированных по классам (positive/neutral/negative/toxic)
2. Разметка данных: команда из 3 модераторов + внешние аннотаторы (Яндекс.Толока / резиденты)
3. Согласованность разметки: Cohen's Kappa ≥ 0.8 между аннотаторами
4. Формирование train/val/test split: 70/15/15, с разделением по времени (test = самые свежие)

#### Фаза 2: Обучение и оценка моделей (недели 3–4)

1. Baseline: легковесная модель (fastText / TF-IDF + Logistic Regression) для сравнения
2. Основная модель: RuBERT fine-tuned на размеченном датасете
3. Оценка на test set с учётом приоритета Recall(toxic) ≥ 0.95
4. Анализ ошибок: confusion matrix, кейс-стади по false positives/negatives

#### Фаза 3: Shadow-режим (недели 5–6)

1. Модель запускается параллельно с ручной модерацией (решения ИИ логируются, но не применяются)
2. Сравнение решений ИИ с решениями модераторов: совпадение, расхождения, их причины
3. Сбор данных для оценки уровня автоматизации: какая доля решений модели совпала бы с модераторами

#### Фаза 4: Анализ результатов и go/no-go решение

#### Критерии успеха пилота

| Критерий | Порог | Измерение |
|---|---|---|
| **Точность классификации** | F1 ≥ 0.92; Recall(toxic) ≥ 0.95 | На тестовой выборке + в shadow-режиме |
| **Доля автоматических решений** | ≥ 70% (при confidence ≥ 0.92) | В shadow-режиме: доля комментариев с confidence ≥ 0.92 |
| **Согласованность ИИ vs модераторы** | Agreement ≥ 85% на эскалационных случаях | Сравнение решений модели и модераторов |
| **Latency инференса** | p95 < 100 мс | Нагрузочное тестирование на 350 RPS |
| **Ложные негативы на toxic** | ≤ 2% от всех toxic-комментариев | Критерий безопасности: пропуск токсичного контента |
| **Покрытие языков/сленга** | ≥ 90% комментариев корректно обработаны | Доля комментариев, где определён язык и применена модель |

## 2. Методология

### 2.1. Тип ML-задачи

Система решает **комбинацию задач классификации**, работающих в ансамбле:

| Задача | Тип | Выход | Приоритет |
|---|---|---|---|
| Тональность комментария | Многоклассовая классификация | positive / neutral / negative / toxic + confidence | Критический |
| Токсичность | Многометочная классификация | toxicity_score [0,1] + субкатегории (insult, threat, hate_speech, obscenity) | Критический |
| Необходимость эскалации | Бинарная классификация | escalate: yes/no (confidence < порог) | Критический |
| Тематика контента | Многоклассовая классификация | news / ad / entertainment / politics / sport / other + confidence | Средний (post-MVP) |

**Почему не регрессия и не рекомендация?** Мы оцениваем дискретные категории (то toxic или не toxic — бинарное решение модерации), а не непрерывные значения. Рекомендательные паттерны здесь не применимы — мы не «рекомендуем» комментарий к удалению, мы классифицируем его состояние.

**Почему ансамбль, а не одна модель?** Токсичность и тональность — ортогональные измерения: нейтральный по тону комментарий может быть токсичным (пассивная агрессия), а негативный — нетоксичным (обоснованная критика). Отдельные модели позволяют независимо настраивать пороги и метрики для каждой задачи.

### 2.2. Данные, необходимые для решения задачи

#### Минимально необходимые данные (без чего задача не решается)

| Данные | Объём | Формат | Назначение |
|---|---|---|---|
| **Текст комментариев** | ≥ 500 000 записей за 6+ месяцев | Текст + metadata (post_id, user_id, timestamp) | Основной признак для классификации |
| **Размеченная выборка тональности** | ≥ 50 000 комментариев, сбалансированных по 4 классам | comment_id → sentiment_label | Train/val/test для модели |
| **Размеченная выборка токсичности** | ≥ 30 000 комментариев, обогащённых toxic примерами | comment_id → toxicity_label + subcategories | Train/val/test для модели токсичности |
| **История модерационных решений** | ≥ 100 000 решений модераторов | comment_id → decision (delete/hide/warn/approve) | Ground truth для оценки; генерация pseudo-labels |

#### Дополнительные данные, повышающие качество

| Данные | Обоснование ценности |
|---|---|
| **Профиль пользователя** (репутация, история нарушений) | Пользователь с 10 нарушениями вероятнее пишет токсичный комментарий |
| **Контекст поста** (категория, автор, заголовок) | Тональность комментария зависит от контекста: «ужасная новость» — негативно о событии, но не токсично |
| **Число лайков/дизлайков на комментарий** | Сигнал одобрения/осуждения сообществом |
| **Цепочка ответов** (parent_comment_id) | Сарказм и ирония часто понятны только в контексте диалога |
| **Время публикации** (час, день недели) | Всплески негатива привязаны к событиям; модель может учесть временные паттерны |

#### Чего точно НЕ нужно (и почему)

| Данные | Причина |
|---|---|
| Персональные данные (ФИО, email, IP) | 152-ФЗ; избыточно для классификации; риск утечки |
| Полные профили пользователей | Приватность; достаточно агрегированной репутации |
| Медиа-вложения (изображения, видео) | MVP фокусируется на тексте; мультимодальность — post-MVP |

### 2.3. Метрики качества и их связь с бизнес-результатом

#### ML-метрики

| Метрика | Формула / определение | Целевое значение | Связь с бизнес-результатом |
|---|---|---|---|
| **F1-score (взвешенный)** | Гармоническое среднее Precision и Recall по 4 классам | ≥ 0.92 | Общая точность системы; напрямую влияет на доверие модераторов |
| **Recall(toxic)** | TP_toxic / (TP_toxic + FN_toxic) | ≥ 0.95 | **Ключевая бизнес-метрика**: пропуск токсичного комментария = потенциальный штраф РКН |
| **Precision(toxic)** | TP_toxic / (TP_toxic + FP_toxic) | ≥ 0.80 | Ложные срабатывания = удаление легитимных комментариев → отток пользователей |
| **Recall(negative)** | TP_negative / (TP_negative + FN_negative) | ≥ 0.85 | Пропуск негатива снижает качество аналитики для рекламодателей |
| **Доля автоматических решений** | comments with confidence ≥ 0.92 / all comments | ≥ 70% (пилот), ≥ 85% (MVP) | Каждый процент автоматизации = экономия человеко-часов модераторов |
| **Калибровка уверенности** | Expected Calibration Error (ECE) | ECE ≤ 0.05 | Корректные пороги уверенности → корректная маршрутизация (автоматическое решение vs эскалация) |

#### Бизнес-метрики

| Метрика | Измерение | Целевое значение | Связь с ML-метрикой |
|---|---|---|---|
| Время реакции на токсичный контент | от публикации до действия | < 30 сек (auto), < 15 мин (escalated) | Прямо пропорционально доле автоматических решений |
| Доля эскалаций модераторам | escalated / total | ≤ 15% | Обратно пропорциональна доле confidence ≥ 0.92; зависит от Recall/Precision модели |
| Согласованность ИИ vs модераторы | Agreement на эскалационных случаях | ≥ 85% | Коррелирует с F1 моделью на пограничных случаях |
| Доля жалоб пользователей | апелляции / удалённые | ≤ 5% | Обратно пропорциональна Precision(toxic): меньше ложных удалений → меньше жалоб |
| Снижение штрафов РКН | штрафы до / штрафы после | ≥ 90% снижение | Прямо пропорционально Recall(toxic) и скорости реакции |
| Стоимость модерации на 1000 комментариев | ФОТ + инфраструктура | ↓ 60% от текущего | Функция от доли автоматизации и стоимости GPU |

#### Приоритизация Recall(toxic) > Precision(toxic)

**Обоснование**: пропуск токсичного комментария (false negative) несёт риск юридических санкций и штрафов РКН. Ложное срабатывание (false positive) — неудобство для пользователя, которое компенсируется возможностью апелляции и эскалацией. Поэтому целевой Recall(toxic) ≥ 0.95 значительно выше целевого Precision(toxic) ≥ 0.80.

### 2.4. Риски на этапе анализа и моделирования

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| **Недостаточно размеченных данных** | Высокая | Критическое: модель не достигнет F1 ≥ 0.92 | 1) Использовать pre-trained RuBERT + fine-tuning (требует меньше данных, чем обучение с нуля) 2) Активное обучение: модель предлагает наиболее неопределённые примеры для разметки 3) Pseudo-labeling на основе решений модераторов 4) Синтетическая аугментация toxic-класса |
| **Несбалансированные классы** | Высокая | Среднее: toxic составляет ~2–5% комментариев, модель_biased к neutral | 1) Stratified sampling при train/val/test split 2) Weighted loss function (увеличенный вес для toxic/negative) 3) Oversampling toxic-класса 4) Focal loss для редких классов |
| **Сарказм, ирония, сленг** | Средняя | Среднее: модель ошибается на подтекстах | 1) Контекстное моделирование (включение parent_comment) 2) Отдельная модель для сарказма (post-MVP) 3) Эскалация неоднозначных случаев (confidence < 0.7) 4) Анализ ошибок и целевая аугментация |
| **Дрейф модели (concept drift)** | Средняя | Высокое: ухудшение качества со временем | 1) Мониторинг метрик в production (Prediction Monitoring) 2) Еженедельная оценка на свежих размеченных данных 3) Автоматическое дообучение при падении F1 ≥ 2pp 4) Canary deployment новых версий |
| **Влияние контекста поста** | Средняя | Среднее: комментарий нейтральный в isolation, но негативный в контексте | 1) Обогащение признаков: category, title, author поста 2) Cross-attention механизмы в модели (post-MVP) 3) Эскалация при расхождении контекстной и безконтекстной оценки |
| **Субъективность разметки** | Средняя | Среднее: низкая согласованность аннотаторов | 1) Cohen's Kappa ≥ 0.8 как критерий приёма данных 2) Кодбук разметки с примерами 3) Мульти-аннотация (≥3 аннотатора на пример) + majority vote 4) Адвокат дьявола: отдельный аннотатор проверяет пограничные случаи |
| **Мультиязычность в комментариях** | Низкая | Низкое: ~90% комментариев на русском | 1) Определение языка (fasttext lid) 2) Для русского — основная модель; для остальных — fallback на эскалацию 3) Post-MVP: расширение моделей на топ-3 языка платформы |

## 3. Подготовка пилота

### 3.1. Способ оценки пилота

Пилот проводится в **shadow-режиме**: модель работает параллельно с ручной модерацией, её решения логируются, но не применяются к реальным комментариям. Это позволяет:

1. **Измерить точность модели в реальных условиях** без риска для пользователей
2. **Оценить уровень автоматизации** (какую долю решений модель приняла бы корректно)
3. **Собрать фидбек модераторов** на решения модели до внедрения в production

#### Схема оценки

| Этап | Метод | Метрики | Длительность |
|---|---|---|---|
| Оффлайн-оценка | Train/val/test split, cross-validation | F1, Recall(toxic), Precision(toxic), ECE | 2 недели |
| Shadow-режим | Параллельная работа модели и модераторов | Agreement rate, False negative rate, Latency | 2 недели |
| A/B-сравнение (опционально) | Случайное разделение трафика: старый процесс vs ИИ | Время реакции, покрытие, жалобы пользователей | 1 неделя |

#### Методика измерения

- **Precision/Recall/F1** — на hold-out test set (отложенная выборка из размеченных данных)
- **Agreement rate** — доля решений модели, совпадающих с решениями модераторов на тех же комментариях
- **False Negative Rate (toxic)** — доля пропущенных токсичных комментариев среди всех токсичных
- **Coverage** — доля комментариев, обработанных моделью с confidence ≥ 0.92
- **Latency** — время от приёма комментария до выдачи решения (p50, p95, p99)

### 3.2. Что считаем успешным пилотом

Пилот считается **успешным** при одновременном выполнении ВСЕХ критериев:

| Критерий | Порог | Обоснование порога |
|---|---|---|
| F1-score (взвешенный) | ≥ 0.90 | На этапе пилота допустима более низкая точность, чем в production (≥ 0.92), с учётом дообучения |
| Recall(toxic) | ≥ 0.95 | Недопустимо пропускать более 5% токсичного контента — прямой риск штрафов РКН |
| Precision(toxic) | ≥ 0.70 | 30% ложных срабатываний допустимы на пилоте — модераторы в эскалации скорректируют |
| Доля автоматических решений (confidence ≥ 0.92) | ≥ 70% | Меньше — не даёт значимой экономии труда модераторов |
| Agreement с модераторами | ≥ 80% | Меньше — система вызывает больше проблем, чем решает |
| Latency p95 | ≤ 200 мс | Превышение → неприемлемая задержка для real-time модерации |
| Доля false negatives на токсичных контекстах | ≤ 3% | Критический порог безопасности |
| Cohen's Kappa аннотаторов | ≥ 0.75 | Ниже → разметка ненадёжна, модель учится на шуме |

**Условия перехода к MVP**: все критерии выполнены → Go. Любой критерий не выполнен → анализ причин, доработка модели, повторный пилот (максимум 1 итерация).

**Критерии провала пилота** (go/no-go):

- Recall(toxic) < 0.90 → риск штрафов неприемлем, система не готова
- F1 < 0.80 → модель ненадёжна, модераторы не доверяют подсказкам
- Доля эскалаций > 40% → автоматизация не даёт значимой экономии

### 3.3. Подготовка пилота

#### Чек-лист подготовки

##### Данные (недели 1–2)

- [ ] Выгрузка 500 000+ исторических комментариев за 6 месяцев (MongoDB dump)
- [ ] Формирование сбалансированного датасета: 50 000+ размеченных, 4 класса, соотношение ~60/20/15/5 (neutral/positive/negative/toxic)
- [ ] Разметка в 3 руки: модераторы платформы + внешние аннотаторы
- [ ] Расчёт Cohen's Kappa между аннотаторами; достижимость ≥ 0.75
- [ ] Train/val/test split 70/15/15 с temporal разделением (test = свежие данные)
- [ ] Анализ дисбаланса классов; подготовка weighted loss

##### Инфраструктура (недели 1–2, параллельно)

- [ ] Kubernetes-кластер с GPU-нодами (NVIDIA A10G или T4) для инференса
- [ ] Prometheus + Grafana для мониторинга метрик
- [ ] Kafka-кластер (3 брокера) с топиками: comment.received, sentiment.result, toxicity.result, decision.made
- [ ] PostgreSQL с развёрнутой схемой данных
- [ ] MongoDB для приёма комментариев
- [ ] Redis для кэширования моделей

##### Модели (недели 3–4)

- [ ] Baseline: fastText / TF-IDF + Logistic Regression (цель: F1 ≥ 0.70)
- [ ] Основная модель: RuBERT fine-tuned (цель: F1 ≥ 0.90)
- [ ] Модель токсичности: RuBERT с отдельным classification head
- [ ] Оценка на test set + анализ ошибок (confusion matrix, кейс-стади)
- [ ] Калибровка confidence (Platt scaling или temperature scaling)

##### Shadow-режим (недели 5–6)

- [ ] Деплой моделей в shadow-режиме (решения логируются, не применяются)
- [ ] Параллельная работа с ручной модерацией
- [ ] Сбор Agreement rate: модель vs модераторы
- [ ] Нагрузочное тестование: 350 RPS, мониторинг latency
- [ ] Анализ расхождений: категоризация случаев несовпадения

|---|---|---|
| API Gateway (auth + routing) | 5 мс | Kong/Nginx |
| Comment Ingestion + Kafka publish | 15 мс | FastAPI + Kafka producer |
| Sentiment Analysis (GPU) | 30 мс | RuBERT, batch processing |
| Toxicity Detection (GPU) | 30 мс | Параллельно с Sentiment |
| Decision Engine | 5 мс | Пороговая логика, DB write |
| PostgreSQL write | 10 мс | ACID commit |

Эскалация модератору добавляет время на ручное решение (минуты), но это ожидаемо и не входит в SLA инференса.

### 4.4. Риски и неопределённости

#### Риски внедрения и их митигация

| # | Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|---|
| R1 | **Модель не достигает F1 ≥ 0.92 в production** из-за расхождения обучающих и реальных данных | Средняя | Критическое: снижение доверия модераторов, отказ от автоматизации | 1) Shadow-режим перед production для валидации 2) Активное обучение на расхождениях ИИ/модераторы 3) Эскалация при низкой уверенности 4) Падение порога автоматизации при необходимости |
| R2 | **Ложные срабатывания (FP) на legit-комментариях** вызывают отток пользователей | Средняя | Высокое: удаление корректных комментариев → жалобы, снижение доверия | 1) Recall(toxic) > Precision(toxic) — приоритет безопасности 2) Порог confidence ≥ 0.92 для автоудаления 3) Система апелляции для пользователей 4) Отдельный порог для «скрытие» vs «удаление» |
| R3 | **Дрейф модели**: качество ухудшается со сменой лексики, трендов, событий | Высокая | Высокое: F1 падает, пропускаются новые формы токсичности | 1) Еженедельный мониторинг Prediction Monitoring (метрики на свежих данных) 2) Автоматическое дообучение при падении F1 ≥ 2pp 3) Canary deployment новых версий 4) Alert на расхождение распределения предсказаний |
| R4 | **Пиковые нагрузки** при вирусных событиях (×5-10 от среднего) | Высокая | Среднее: рост latency, потенциальные таймауты | 1) Kubernetes HPA + GPU-автомасштабирование 2) Kafka буферизация (потребляет пики) 3) Rate limiting на API Gateway 4) Shedding: при перегрузке fallback на эскалацию всех (не теряем покрытие) |
| R5 | **Штрафы РКН при сбоях ИИ** | Низкая | Критическое: юридические последствия | 1) Graceful degradation: при недоступности ИИ → fallback на полную ручную модерацию 2) Мониторинг покрытия: alert при < 100% обработке 3) Аудит-лог для РКН 4) SLA на availability 99.9% |
| R6 | **Сложность运维 (operational complexity)**: 5 БД, Kafka, Kubernetes, GPU-инференс | Высокая | Среднее: затраты на DevOps, риск длительных инцидентов | 1) IaC (Terraform + Helm charts) для воспроизводимости 2) Observability: distributed tracing (Jaeger), logs (ELK), metrics (Prometheus) 3) On-call rotation документация 4) Старт с минимального набора (PostgreSQL + Kafka + Redis + 1 GPU) |
| R7 | **Утечка данных / нарушение 152-ФЗ** | Низкая | Критическое: штрафы до 18 млн ₽, репутационный ущерб | 1) Минимизация ПДн в ML-пайплайне (хэширование идентификаторов) 2) Шифрование at-rest + in-transit 3) Аудит доступа к данным 4) DLP-мониторинг |
| R8 | **Команда из 2-3 человек не справляется** с масштабом | Средняя | Высокое: задержки, технический долг приоритизируется неправильно | 1) Чёткое разделение ролей (Product Owner / Data Architect / Data Engineer) 2) Использование managed-сервисов где возможно (Cloud Kafka, RDS) 3) Приоритизация: MVP — только критические компоненты 4) Автоматизация CI/CD и monitoring с первого дня |
| R9 | **Resistance со стороны модераторов**: нежелание принимать подсказки ИИ | Средняя | Среднее: не используют подсказки, игнорируют систему | 1) Пилот с добровольцами из числа модераторов 2) Обучение: демонстрация что ИИ экономит время, а не заменяет 3) Показатели: «вы обработали в 5 раз больше с ИИ» 4) Геймификация: статистика принятых/отклонённых подсказок |
| R10 | **Модель показывает bias**: несоразмерно удаляет комментарии определённых групп | Низкая | Высокое: юридический и репутационный риск | 1) Анализ bias по демографическим и тематическим группам перед production 2) Fairness-метрики: demographic parity, equalized odds 3) Регулярный аудит: monthly bias report 4) Возможность ручной настройки порогов по категориям |

#### Неопределённости, требующие дополнительного исследования

1. **Модель для сарказма/иронии**: нет ясного понимания, насколько сарказм распространён в комментария и как его качество влияет на общий Recall. Требуется отдельный анализ на размеченных данных.

2. **Оптимальный порог confidence**: целевое значение 0.92 — оценка, основанная на best practices. Точный порог будет уточнён на основе shadow-режима (анализ распределения confidence на реальных данных).

3. **Стоимость GPU-инференса в production**: расчёт основан на ценах AWS (on-demand). Резервирование или spot-инстансы могут снизить стоимость в 2-3x, но требуют обязательства по сроку.

4. **Влияние контекста поста на точность**: неизвестно, насколько добавление контекста (категория, заголовок) улучшит F1. Требуется A/B-сравнение модели с контекстом и без.

5. **Динамика объёма комментариев**: прогноз 500K/день — среднее значение. Вирусные события могут давать ×10 всплески. Архитектура должна быть готова, но точный масштаб пиков требует мониторинга реального трафика.
