# Структура и распределение данных в системе

## 1. Схема структуры данных (ER-диаграмма)

Для надежного функционирования информационной системы спроектирована гибридная реляционно-аналитическая модель данных.

![ER-диаграмма данных](https://raw.githubusercontent.com/lk2322/ml-system-design-sentiment/docs-diagrams-setup/docs/assets/diagrams/er_diagram.svg)

### Описание сущностей реляционной БД (PostgreSQL):
- **users** — Хранит информацию о пользователях социальной сети. Содержит репутационный скор (влияющий на пороги срабатывания автоматических фильтров) и статус учетной записи.
- **comments** — Основная транзакционная таблица комментариев. Содержит сырой текст, уникальный идентификатор и внешний ключ на пользователя.
- **ml_sentiment_results** — Хранит выводы ИИ-модели по каждому комментарию: категорию (label), вероятность (confidence) и уровень токсичности (toxicity_score). Связь с родительской таблицей комментариев 1:1.
- **moderation_actions** — Журнал выполненных действий. Хранит информацию о типе модерации (автоматическое скрытие модели или ручное вмешательство ассистента-модератора) и обоснование принятого решения.

### Описание аналитической структуры хранения (ClickHouse):
- **moderation_analytics** — Денормализованная плоская таблица, оптимизированная по колоночному типу для выполнения сверхбыстрых OLAP-запросов и построения дашбордов. Позволяет мгновенно получать срезы негатива по часам, дням и платформам при нагрузке 500 000 записей ежедневно.

## 2. Обоснование распределенного характера хранения данных

Работа с данными в проектируемой ИИ-системе носит распределенный характер по следующим технологическим и архитектурным причинам:

### 1. Архитектурное разделение нагрузки (Pattern CQRS)
- **OLTP-слой (PostgreSQL Sharded):** Обрабатывает интенсивные транзакции на запись и чтение в реальном времени при отрисовке комментариев в пользовательском интерфейсе. Данный слой шардируется горизонтально по ключу `user_id` (или `platform_id`), чтобы исключить единую точку отказа при пиковых нагрузках сотен параллельных соединений.
- **OLAP-слой (ClickHouse Analytics):** Используется для долгосрочного хранения денормализованной истории результатов модерации. Реляционные СУБД вроде Postgres крайне неэффективны при агрегации миллионов строк (например, при расчете вовлеченности или темпов роста негатива за месяц). ClickHouse с легкостью решает эту задачу на минимальном оборудовании.

### 2. Масштабируемость семантического и контекстного поиска
- **Слой поиска (Elasticsearch/OpenSearch):** Модераторы и аудиторы качества должны обладать средством поиска по ключевым словам и паттернам токсичности по всей истории комментариев. Elasticsearch выносится в отдельный распределенный кластер, поддерживая инвертированные индексы текстов комментариев, что разгружает основные рабочие базы данных от тяжелых текстовых запросов `LIKE`.

### 3. Кэширование горячих данных и очередей
- **Слой быстрых данных (Redis Cluster):** Используется для мгновенной дедупликации частых повторных отправлений (анти-спам защита по скользящему временному окну) и хранения метаданных состояния сессий модераторов. Также Redis выступает в роли распределенного брокера временных задач для планировщиков очередей.

### 4. Обеспечение отказоустойчивости (Fault Tolerance)
Распределенное хранилище гарантирует бесперебойную работу пользовательского приложения. В случае временного сбоя аналитического кластера ClickHouse или поискового Elasticsearch, базовая функция публикации комментариев в PostgreSQL продолжает работать в штатном режиме через шину сообщений Kafka. Данные будут доставлены в OLAP после восстановления доступности принимающих слоев.
