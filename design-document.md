## 1. Цели и предпосылки

### 1.1. Зачем идём в разработку продукта?

Социальная сеть ежедневно принимает до **500 000 комментариев**. Ручная модерация покрывает менее 5% этого объёма, что создаёт:

- **Юридический риск**: РКН (Роскомнадзор) мониторит качество модерации; неприемлемый контент, оставшийся опубликованным, влечёт штрафы до миллионов рублей и риск блокировки.
- **Репутационный риск**: Токсичная среда отталкивает пользователей, снижает вовлечённость и рекламный доход.
- **Операционные затраты**: 30+ модераторов в смену — costly и некачественно (субъективность, текучка, медленное время реакции).

**Цель продукта**: Автоматизировать анализ тональности комментариев в реальном времени с помощью ML-модели, обеспечив 100% покрытие входящего потока, сокращение времени реакции с часов до секунд и снижение стоимости модерации минимум в 3 раза.

### 1.2. Почему станет лучше, чем сейчас, от использования ML?

| Аспект | Без ML | С ML |
|---|---|---|
| Покрытие | < 5% комментариев | 100% — каждый комментарий анализируется |
| Скорость | 2–24 часа до решения | < 1 секунда (автоматически), < 15 мин (человек для граничных) |
| Стоимость | 30+ модераторов | 5–7 модераторов для граничных случаев |
| Объективность | Субъективные решения | Консистентная модель + человеческий контроль |
| Аналитика | Отсутствует | Дашборд тональности в реальном времени |
| Обучаемость | Нет обратной связи | Дообучение на сигналах модераторов |

**Ключевой аргумент**: ML не заменяет модераторов полностью, а **аугментирует** их работу — модель берёт на себя 95%+ рутинных решений, оставляя человеку только граничные случаи. Это парадигма *human-in-the-loop*.

### 1.3. Бизнес-требования и ограничения

**Бизнес-требования**:
- BR-1: Система должна обрабатывать ≥ 500 000 комментариев/день (≈ 6 RPS sustained, пики до 20 RPS).
- BR-2: Время от публикации комментария до автоматического решения — не более 2 секунд (P95).
- BR-3: Recall негатива (доля пойманных негативных комментариев) ≥ 95%: лучше перестраховаться, чем пропустить нарушение.
- BR-4: Precision ≥ 80%: допустимы ложноположительные срабатывания (модератор проверит), но не ложноотрицательные.
- BR-5: Соответствие требованиям РКН: автоматическое скрытие потенциально нарушающего контента до ручной проверки.
- BR-6: Возможность дообучения модели на основе обратной связи модераторов.

**Ограничения**:
- CON-1: Данные пользователей (комментарии) — персональные данные, обработка по 152-ФЗ.
- CON-2: Модель должна поддерживать русский язык как основной.
- CON-3: Инфраструктура должна быть размещена на территории РФ (data sovereignty).
- CON-4: Бюджет MVP — до 2 млн руб. на инфраструктуру + 3 человек × 3 месяца на разработку.
- CON-5: Интеграция с существующей системой авторизации и контент-менеджмента.

### 1.4. Функциональные и нефункциональные требования

**Функциональные**:
- FR-1: API приёма нового комментария с синхронным возвратом статуса публикации.
- FR-2: Асинхронный конвейер анализа тональности с записью результата.
- FR-3: Автоматическое скрытие комментариев с негативностью ≥ 0.85.
- FR-4: Направление комментариев с негативностью 0.5–0.85 в очередь на ручную модерацию с подсказкой ИИ.
- FR-5: Модераторский дашборд: очередь, предзаполненные рекомендации, кнопка подтверждения/отклонения.
- FR-6: Аналитический дашборд: тренды тональности по темам, процент негатива, статистика модерации.
- FR-7: Сбор сигналов обратной связи (модератор не согласен с ИИ) и накопление для дообучения.
- FR-8: Периодическое дообучение модели (еженедельно / по накоплении ≥ N сигналов).

**Нефункциональные**:
- NFR-1: Доступность системы — 99.9% (SLA).
- NFR-2: Latency предсказания — ≤ 100 мс на комментарий (P95).
- NFR-3: Масштабируемость: горизонтальное масштабирование inference-серверов.
- NFR-4: Наблюдаемость: логирование, метрики (Prometheus + Grafana), алертинг.
- NFR-5: Безопасность: шифрование данных в покое и при передаче (TLS 1.3).
- NFR-6: Резервное копирование данных PostgreSQL — ежедневно, ClickHouse — ежедневно, модели S3 — при каждом деплое.
- NFR-7: Аудит: все действия модераторов логируются с возможностью восстановления.

### 1.5. Процесс пилота и критерии успеха

**Фаза пилота (4 недели)**:

| Неделя | Деятельность |
|---|---|
| 1 | Деплой модели на staging, подключение к 10% трафика (shadow mode — логируем, не блокируем) |
| 2 | Анализ расхождений модель vs модераторы, калибровка порогов |
| 3 | Включение автоматического скрытия для confidence ≥ 0.9, ручная очередь для 0.5–0.9 |
| 4 | Полное включение с текущими порогами, сбор метрик |

**Критерии успеха пилота**:
- Recall негатива ≥ 90% на тестовом потоке (цель MVP — ниже продакшн-цели, но выше ручного покрытия).
- Precision ≥ 75% (ложноположительные терпимы на этапе пилота).
- Latency P95 ≤ 2 секунды end-to-end.
- Модераторы подтверждают ≥ 80% рекомендаций ИИ.
- Не более 5% жалоб пользователей на неправомерное скрытие комментариев.

### 1.6. Состав итерации MVP vs технический долг

**Входит в MVP**:
- Inference API для анализа тональности (бинарная модель: негатив/не-негатив).
- Простое пороговое правило (0.5 / 0.85) для маршрутизации.
- Модераторский дашборд с очередью и рекомендациями.
- Сбор feedback-сигналов в ClickHouse.
- Базовый аналитический дашборд (тренды тональности по дням).
- CI/CD для модели (ручной деплой новой версии).

**Технический долг (итерации 2+)**:
- Дообучение модели в автоматическом режиме (MVP — ручной запуск).
- Мультиязыковая поддержка (MVP — только русский).
- Многоклассовая тональность (позитив / нейтральный / негатив / токсичный) вместо бинарной.
- Интеграция с рисками РКН: автоматические отчёты.
- A/B тестирование моделей (canary deployment).
- Продвинутый аналитический дашборд: дрифт-мониторинг, объяснимость предсказаний (SHAP/LIME).
- Контекстный анализ (учёт темы поста, истории пользователя).

## 2. Методология

### 2.1. Техническая задача

**Задача**: мультиклассовая классификация тональности коротких текстов (комментариев) на русском языке с акцентом на обнаружение негативного и токсичного контента.

Формально: для входного текста комментария `x` модель вычисляет распределение `P(y|x)`, где `y ∈ {positive, neutral, negative_low, negative_high, toxic}`. На основе уверенности модели принимается решение о маршрутизации:

- `P(toxic | x) ≥ 0.85` → автоматическое скрытие.
- `P(negative | x) ∈ [0.5, 0.85)` → очередь на ручную модерацию.
- `P(negative | x) < 0.5` → автоодобрение.

### 2.2. Необходимые данные

| Данные | Источник | Обязательно? | Назначение |
|---|---|---|---|
| Исторические комментарии (≥ 1 млн) с разметкой тональности | Экспорт из БД соцсети + ручная/краудсорсинг разметка | Да, критично | Обучающая выборка |
| Словари стоп-слов и токсичных выражений (русский язык) | Публичные датасеты + внутренние | Да | Фильтрация + признаки |
| Информация о пользователях (trust_score, история нарушений) | User Service (PostgreSQL) | Желательно | Контекст: рецидивисты vs новички |
| Тематическая привязка постов | Post Service + тематические модели | Желательно | Контекст: допустимая тональность варьируется по темам |
| Логи модерации (история удалений / одобрений) | Moderation Service (PostgreSQL) | Да, для дообучения | Обратная связь от людей |
| Штрафы и предписания РКН | Внешний источник / ручной ввод | Желательно | Валидация полноты покрытия |

**Без чего нельзя**: исторические комментарии с разметкой тональности. Минимум 100K размеченных примеров с балансом классов. Без этого модель не обучить.

### 2.3. Метрики качества ML и связь с бизнес-результатом

| ML-метрика | Определение | Бизнес-связь |
|---|---|---|
| Recall (negative/toxic) | Доля реально негативных комментариев, обнаруженных моделью | Напрямую связана с риском штрафов РКН: чем выше recall, тем меньше пропущенных нарушений |
| Precision (negative/toxic) | Доля предсказанных негативных, которые реально негативные | Связана с нагрузкой на модераторов: низкий precision = больше ложноположительных = лишняя работа |
| F1-score (weighted) | Гармоническое среднее precision и recall | Баланс покрытия и точности; трекинг общего качества модели |
| ROC-AUC | Площадь под ROC-кривой | Агрегированная оценка разделимости; мониторинг деградации во времени |
| Latency (P95) | Время инференса на один комментарий | Время реакции системы напрямую влияет на длительность публикации негативного контента |

**Целевые значения для продакшена**:
- Recall (negative + toxic) ≥ 95% — приоритет: лучше перестраховаться.
- Precision ≥ 80% — допустимый уровень ложноположительных.
- F1 ≥ 0.85.
- ROC-AUC ≥ 0.90.
- Latency P95 ≤ 100 мс.

### 2.4. Риски на этапе анализа и моделирования

| Риск | Вероятность | Влияние | Планируемая реакция |
|---|---|---|---|
| Недостаток качественных данных для русского языка | Высокая | Высокое | Краудсорсинг разметки + augmentations (перефразирования); рассмотреть transfer learning с мультиязычных моделей |
| Дисбаланс классов (негативных комментариев ~5-10%) | Высокая | Среднее | Weighted loss, oversampling негативного класса, focal loss |
| Концептуальный дрифт (смена сленга, новые оскорбления) | Средняя | Высокое | Периодическое дообучение (еженедельно); мониторинг дрифт-метрик на входящих данных |
| Ложноотрицательные на сарказме/иронии | Средняя | Среднее | Отдельный класс «sarcasm» в итерации 2+; на MVP — перенос в ручную очередь при низкой уверенности |
| Высокая латентность модели (BERT-family) | Средняя | Высокое | DistilBERT / ruBERT-tiny для inference; batch-предсказания для пиковой нагрузки |
| Утечка персональных данных | Низкая | Критическое | Хранение текстов в зашифрованном виде; анонимизация логов; доступ по ролям |

## 3. Подготовка пилота

### 3.1. Способ оценки пилота

Оценка пилота проводится в три этапа:

1. **Offline-оценка**: модель тестируется на отложенной выборке (20% от размеченных данных) с расчётом Recall, Precision, F1, ROC-AUC.
2. **Shadow mode (неделя 1–2)**: модель работает параллельно с текущим процессом модерации, логируются все предсказания, но не влияют на публикацию. Сравниваем модель vs ручные решения модераторов.
3. **Active mode (неделя 3–4)**: модель принимает автоматические решения (скрытие негатива с confidence ≥ 0.9), граничные случаи — в очередь модераторам. Отслеживаем: процент авто-действий, подтверждённость рекомендаций модераторами, жалобы пользователей.

### 3.2. Критерии успешного пилота

| Критерий | Порог |
|---|---|
| Recall негатива + токсика | ≥ 90% |
| Precision | ≥ 75% |
| Latency P95 end-to-end | ≤ 2 секунды |
| Подтверждение рекомендаций ИИ модераторами | ≥ 80% |
| Жалобы на неправомерное скрытие | ≤ 5% от авто-скрытых |
| Доступность системы | ≥ 99% за период пилота |

### 3.3. Подготовка пилота

**Инфраструктура**:
- Staging-окружение: Kubernetes cluster (минимум 3 ноды), PostgreSQL, ClickHouse, Kafka, Redis, S3.
- ML-модель: ruBERT-tiny / cointegrated/rubert-tiny2, дообученная на размеченных данных.
- Мониторинг: Prometheus + Grafana для метрик модели и системы.

**Данные**:
- Обучающая выборка: ≥ 100K комментариев с ручной разметкой (5 классов).
- Валидационная выборка: 20K, тестовая: 20K.
- Если внутренней разметки недостаточно → краудсорсинг (Toloka / Яндекс.Толока).

**Персонал**:
- 2 модератора для проверки граничных случаев на pilot.
- 1 data scientist для мониторинга метрик и калибровки.
- 1 DevOps/инженер для поддержки инфраструктуры.

**Процесс**:
- Двойная проверка: на shadow mode каждый комментарий получает оценку модели и модератора, расхождения логируются.
- Калибровка порогов: по итогам недели 1–2 подбираются оптимальные пороги auto-hide и review-queue.
- Rollback plan: при падении Recall ниже 85% или Precision ниже 70% — откат на ручной процесс + анализ ошибок.

## 4. Внедрение для production системы

### 4.1. Архитектура решения

См. диаграмму архитектуры: [`diagrams/architecture.md`](diagrams/architecture.md)

**Общая архитектура** — событийно-ориентированная (event-driven) с микросервисной декомпозицией:

| Компонент | Назначение |
|---|---|
| **API Gateway / Load Balancer** | Единая точка входа, rate limiting, TLS-терминация, маршрутизация |
| **Comment Service** | CRUD комментариев, запись в PostgreSQL, публикация событий в Kafka |
| **Post Service** | Управление постами, метаданные для контекстного анализа |
| **User Service** | Профили пользователей, trust_score, история нарушений |
| **Moderation Service** | Управление очередью модерации, действия модераторов, логирование |
| **Analytics Service** | Агрегация данных из ClickHouse, построение дашбордов |
| **Inference API Service** | ML-предсказания: тональность, токсичность. Модель загружается из S3 |
| **Preprocessing Module** | Очистка текста, токенизация, генерация эмбеддингов |
| **Message Queue (Kafka)** | Асинхронная передача событий между сервисами |
| **Retraining Pipeline** | Периодическое дообучение модели на сигналах обратной связи |

**Распределённое хранение данных** обосновано разными паттернами доступа (см. [`diagrams/er-data-model.md`](diagrams/er-data-model.md)):

| Хранилище | Данные | Причина |
|---|---|---|
| PostgreSQL | User, Post, Comment, ModerationAction, ModelMetadata | OLTP, ACID, реляционная целостность |
| ClickHouse | SentimentReport, FeedbackSignal | OLAP, колоночное сжатие, быстрые агрегации |
| Redis | Кэш предсказаний, сессии | Sub-ms latency, TTL, in-memory |
| S3 | Артефакты моделей (веса, конфиги) | Большие бинарные файлы, версионирование |

### 4.2. Описание инфраструктуры и масштабируемости

**Выбранная инфраструктура**: Kubernetes (K8s) на управляемом кластере (Yandex Cloud / Selectel — для соответствия data sovereignty, CON-3).

**Почему K8s**:
- Горизонтальное масштабирование inference-подов под нагрузку (HPA по CPU/RPS).
- Rolling deployments для моделей без даунтайма.
- Единая платформа для всех микросервисов.

| Плюсы | Минусы |
|---|---|
| Эластичное масштабирование | Сложность эксплуатации K8s |
| Rolling updates, canary deployments | Overhead на управление кластером |
| Единая платформа для всей системы | Vendor lock-in (смягчается Terraform/IaC) |
| Self-healing, health checks | Требуется DevOps-экспертиза |

**Масштабируемость**:
- Inference Service: HPA (Horizontal Pod Autoscaler) от 2 до 20 реплик по RPS.
- Kafka: 3 брокера, partitioning по comment_id.
- ClickHouse: распределённая таблица на 2 шарда, репликация через ZooKeeper.
- PostgreSQL: primary-replica с репликой для чтения аналитики.

**Ресурсы для MVP**:
- 3 ноды K8s (4 CPU / 16 GB RAM каждая) — контроллер + inference + сервисы.
- GPU: 1 × NVIDIA T4 для inference (batch-предсказания при пиках).
- Persistent volumes: PostgreSQL — 100 GB, ClickHouse — 500 GB, S3 — 50 GB.

### 4.3. Требования к работе системы

| Параметр | Значение | Обоснование |
|---|---|---|
| SLA (доступность) | 99.9% | Социальная сеть: простой = нескрытый негатив |
| RPS (sustained) | 6 RPS | 500K комментариев / 86400 секунд |
| RPS (пиковый) | 20 RPS | Утренний / вечерний пик × 3–3.5 |
| Latency (inference) | ≤ 100 мс P95 | Модель на GPU, batch-оптимизация |
| Latency (end-to-end) | ≤ 2 сек P95 | От публикации до решения о модерации |
| Recovery Time Objective | ≤ 15 мин | Автоматический failover в K8s |
| Recovery Point Objective | ≤ 1 час | Частые бэкапы PostgreSQL / ClickHouse |

### 4.4. Риски и неопределённости

| Риск | Влияние | Митигация |
|---|---|---|
| Концептуальный дрифт модели | Снижение Recall / Precision со временем | Мониторинг дрифт-метрик, еженедельное дообучение, автоматический откат при деградации |
| Взлом / adversarial атаки на модель | Злонамеренный обход фильтров | Ensemble моделей, проверка на известных атаках, rate limiting |
| Потеря данных (PostgreSQL / ClickHouse) | Невозможность дообучения и аналитики | Репликация, ежедневные бэкапы, S3 для моделей |
| Рост объёма комментариев сверх прогноза | Деградация latency | HPA для inference, партиционирование Kafka, шардирование ClickHouse |
| Изменение законодательства (РКН) | Новые категории контента к модуляции | Гибкая система классов, быстрое добавление новых категорий через дообучение |
| Нехватка GPU для inference | Перегрузка модели | Fallback на CPU-inference (с更高的 latency), приоритизация по рискам |
| Зависимость от одного cloud-провайдера | Vendor lock-in | IaC (Terraform), контейнеризация, S3-совместимое API |
